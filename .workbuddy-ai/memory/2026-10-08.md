## rotate-rs：Hybrid 模式"同一秒出现 .1/.2 两个空文件"排查

用户报告（未改代码，仅分析）：Hybrid 模式、每 10s 切割时，出现 `app.<date>.2.log`，
以及 `app.2026-10-08-22-15-36.1.log` 与 `.2.log` 两个**空文件同秒**。

### 结论（已用临时 example 复现，跑完删除，仓库保持干净）
1. 命名规则 `{dir}/{name}{sep}{date}{sep}{counter}{sep}{suffix}`，`{date}` 为
   `%Y-%m-%d-%H-%M-%S`（**秒级精度**）。engine.rs 轮转时用 `create_new` 占位探测，
   同名冲突则 counter++ → 因此"**同一秒内发生 ≥2 次轮转**"必然产生 `.1/.2/.3`。
   `.2` 不是命名 bug，而是"同秒双轮转"的必然结果。
2. **空文件**：rotate_inner 不做"活跃文件为空则跳过"的判断；NonBlocking 的定时器
   在空闲时仍按周期触发轮转 → 把 0 字节的活跃文件归档成空文件。
3. 复现证据（interval 缩短以加速）：
   - 单实例 空闲 + interval=100ms：22:21:55 出现 .1/.2/.3，56 出现 .1~.5，全部 0B。
   - **多实例**（同目录 2~3 个 Writer）：空闲时同秒 `.1/.2`（0B）；写入时同秒
     `.1(144B)/.2(160B)` —— 与用户现象完全一致。
   - max_size 很小（300B）时：每秒多次 size 轮转 → 同秒 .1/.2/.3（但文件非空）。

### 附带发现的两个独立 bug
- **时间轮转周期≈配置值的 2 倍**：channel.rs 超时分支用旧 deadline `+= iv` 推进，
  而 `last_rotation` 在轮转完成时才置为 now（晚于 deadline）→ 下一次超时
  `elapsed = iv - ε < iv` 被跳过，实际隔一个周期才轮转。实测 interval=1s → 2s 一次。
- **空文件归档**：应跳过 `current_size == 0` 的轮转（只重置定时器）。

### 待用户确认
实际 interval 取值、是否单实例、max_size 是否真的未达、写入模式（Sync/NonBlocking）。

## 新问题（仅分析出方案，未改代码）：运行期活跃文件被删 → `rotate-retry: I/O 错误: 系统找不到指定的文件 (os error 2)`

### 根因
`Engine::rotate_inner`（engine.rs:223）隐含假设"活跃文件在磁盘上一定存在"，三级恢复链
只覆盖"打开新活跃文件失败"，**不覆盖"rename 源文件消失"**：
- 文件被外部删除后，`file` 仍是旧句柄、`current_size=N>0`（零字节跳过不生效）
- 阶段二 `create_new` 占位成功（目录还在）→ 阶段三 `fs::rename(active_path, target)`
  因**源不存在**返回 `NotFound` → 删占位、返回 `Err` → 置 `last_rotation_error`
- 之后每次 write 命中 `has_pending_rotation()` → 无条件重试 → rename 永远 NotFound
  → **永久卡死**，报 `rotate-retry`；`last_rotation_error` 永不清除
- 附带：旧句柄继续收写入（Linux 静默写进 unlinked inode = 数据静默丢失）

### 方案（推荐 A）
- **A（推荐）**：`rotate_inner` 在**零字节跳过之前**先探测 `active_path.try_exists()`；
  缺失 → 丢弃旧句柄 + `create_dir_all(parent)` + `create(true).append(true)` 重开
  + `current_size = metadata().len()` + `finish_rotation()`（清错+推进时间基准）→ 返回 `Ok`。
  再补阶段三 rename 的 `NotFound` 兜底（TOCTOU）。顺带能自愈"三级恢复全失败 → Writer 永久不可用"。
  探测顺序必须在零字节跳过之前，否则空文件被删时会被跳过而不重建。
- **B（可选增强）**：写入路径加**节流**存在性检查，覆盖"未到轮转点也被删"（有 syscall 开销）。
- **C（最小改动，不推荐）**：只把 rename 的 NotFound 当"无源可归档"，跳过归档直接进阶段五；
  语义混淆（`current_size`/`last_rotation_key` 错位），且漏 flush/sync 阶段的 NotFound。

### 空文件风险复核（用户确认选 A 后追问）
结论：**A 本身不产生任何归档文件**（只重建活跃文件），不会重现"空闲空归档"。
唯一要盯住的是 **TOCTOU 分支**：入口探测通过后，阶段二 `create_new` 已产生 0 字节占位；
若阶段三 rename 才 NotFound，**必须先 `remove_file(&target)` 删占位再重建**，否则残留
0 字节"伪归档"。常规路径（进入 rotate 前文件已删）在阶段二之前就被探测拦截，不会建占位。
重建后活跃文件为 0 字节属正常，后续由既有零字节跳过（`current_size==0 && file.is_some()`）
保证不会被归档成空文件。

### 实施记录（方案 A 已落地）
- `src/engine.rs`：
  - `rotate_inner` 入口（**零字节跳过之前**）新增 `if self.active_file_missing() { return self.reopen_active()... }`；
  - 阶段三 rename 失败分支：`NotFound && active_file_missing()` 时同样走 `reopen_active`，
    而不是返回 Err（原 `remove_file(&target)` 占位清理保留，避免 0 字节伪归档）；
  - 新增两个私有方法：`active_file_missing()`（`!try_exists().unwrap_or(true)`，Err 按"存在"处理）
    与 `reopen_active()`（丢弃旧句柄 → `create_dir_all(parent)` → `create(true).append(true)` 打开
    → 从 metadata 恢复 `current_size` → `finish_rotation()`）。
- `src/lib.rs`：使用约束新增第 6 条，说明"活跃文件被外部删除会自动重建，不产出归档、不报错，
  删除前未落盘数据无法找回"。
- `tests/rotation.rs`：新增 `deleted_active_file_is_recreated_on_rotation`（含 error_handler 断言
  恢复过程零上报）与 `rotation_still_works_after_recovery`（恢复后仍能正常产出归档）。
- 验证：`cargo test` 4/4 通过；`git stash` 还原 `src/engine.rs` 后两个新测试均失败
  （"活跃文件应被重建"）→ 确认为真回归测试。clippy 警告数与基线一致（5，均为既有
  `fetch_update` deprecation 与测试里的 `&PathBuf`）；`cargo fmt` 差异为既有 import 排序，未触碰。

### 方案 D 提案（覆盖"未到轮转点被删"的遗留边界，仅方案未改代码）
现状：检测只在 `rotate_inner`（入口 + rename TOCTOU），而 `rotate()` 被
`should_rotate_now/by_size` 门控 → 文件被删但未到轮转点时永不探测，
写入静默落入旧句柄（Linux unlinked inode / Windows delete-pending）。

**方案 D（推荐）：`Engine::write_all` 开头的节流存在性检查**
- Engine 新增 `last_active_check: Instant`；config.rs 新增
  `ACTIVE_FILE_CHECK_INTERVAL: Duration = 1s`。
- `write_all` 写入**之前**：`now.saturating_duration_since(last_active_check) >= INTERVAL`
  → 更新 last_active_check → `active_file_missing()` → `reopen_active()`；
  失败经 reporter 上报（context "recover"），**不阻断写入**（沿用既有
  "轮转问题不阻断写入"约定），下一节流窗口自愈重试。
- 覆盖 Sync + NonBlocking（NonBlocking 下 `write_all` 在 worker 线程，
  业务线程零额外开销；Sync 下多一次 `Instant::now()`，~20ns）。
- 代价：每 write 一次时钟读取（Sync 本来就有一次）；每 1s 一次 stat。
- 检测延迟 ≤ 1s → 最多丢 ~1s 写入。无法做到 0，除非每次 write 都 stat。
- 已知不覆盖：删除后立即被外部重建同名文件（`try_exists` 判存在，仍写旧 inode）；
  要覆盖需比较 dev+ino（Unix `MetadataExt::ino`；Windows `file_index` 仍不稳定）。

**备选**：E. Windows 用 `OpenOptionsExt::share_mode` 去掉 `FILE_SHARE_DELETE` 防删除
（仅 Windows，且改变"外部删除失败"行为）；F. worker `recv_timeout` 上限压到 1s
做空闲探测（空闲无写入=无丢失，收益小，且 Sync 无 worker 仍需 D）。

**测试思路**：Size 阈值 1GB + interval 1h 保证不触发轮转 → 写一笔 → 删文件 →
等 >1s → 再写 → 断言文件被重建且内容正确（修复前写进已删句柄，断言失败）。
